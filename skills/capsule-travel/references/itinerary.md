# Daily itinerary

Use the user's chosen or booked accommodation as the base. If none is chosen, clearly mark an assumed base and avoid presenting resulting journeys as final. Work for the requested destination; there is no built-in geographic catalog.

Cover the arrival and departure dates as well as full days. Ask arrival/departure times when needed; until known, keep those days free or explicitly provisional. Group visits by geography and the user's interests. Check opening days, dated closures, reservations and admission from current sources before assigning a time-sensitive stop. If not checked, use a provisional time window and say what remains unresolved.

Use a map or routing source for the chain accommodation → stop A → stop B → accommodation. If no routing tool is available, link to map directions or mark travel times unverified; don't invent exact walking minutes from straight-line distance. Mention estimates and source date. Never call a route accessible without supporting access details. Compare each leg and the daily total with the user's actual tolerance, keeping unknown legs distinct from a complete total.

Tie each visit or block to an existing outfit ID and a short reason based on the planned activity and known clothing properties. Use varied combinations while reusing basics. A wardrobe does not prove compliance with a venue's dress code: check the venue when relevant. Weather-sensitive choices should include a practical alternative based on known protection, not assumed fabric properties.

When an outfit changes during the day, allow for changing clothes. Route back through the accommodation and include both legs and a changing break, or agree another realistic arrangement. Do not teleport the traveler or their luggage between stops. Include useful rest and meal time rather than overpacking the day.

Show a compact chat table: date, places in order, outfit, travel time or uncertainty, and one important constraint. Provide outfit visuals when supported, and linked sources for important restrictions or journey estimates. A full itinerary may need more text than an ordinary turn. Don't send the user to a separate website to see Capsule's result; external source and booking links are references, not an alternative user interface.

After a change, update affected stops, outfit references and journeys together. Keep unverified bookings, opening hours and transport visibly distinct from confirmed choices. The itinerary is a proposal until the user accepts it; selecting a hotel is not a reservation.
